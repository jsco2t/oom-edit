# Bounded interaction feasibility decision

Decision: **GO, with a narrow interior-fence fast path and explicit full-parser fallback.** The existing one-owner `LiveDocument` / one-`EditorSession` architecture can plausibly meet the round-2 ordinary-edit and Select targets. This is a feasibility decision, not acceptance of the current production behavior or a claim that all user-visible paths already meet 50 ms. No loading state, stale editable frame, second mutable text copy, new parser or host-specific renderer is needed.

## Measured constraint and opportunity

Task 013 shows that a 15-line deletion in either ~390 KiB fence takes about 4.5 seconds through a completed candidate pane frame, versus ~2.2–2.4 seconds on clean main, and leaves source lines behind. The candidate's projected selection produces 14–15 small `TextEdit`s; `LiveDocument::refresh_derived` processes them one at a time, and each enters `RetainedBlockModel`'s full-rebuild branch because the fence exceeds 8 KiB. The test-only work trace reported 2,387 rebuilt blocks and about 1,048,400 parsed Markdown bytes. Normal rendered navigation itself was not slow in the pane or PTY proxy. Select's full-source projection takes about 16–41 ms per call, and the pane requests it more than once per visible frame.

The following same-machine release measurements use the exact 1,048,722-byte fixture, with fresh full builds as correctness oracles. Times are single-run feasibility samples unless otherwise stated, not p99 promises:

The source fast-path prototype accepts only a full-line edit strictly within an already-known fence body, rejects potential fence-marker lines, and incrementally reparses its retained injection tree. It applies a positional edit to the Markdown block tree without reparsing that opaque code body. It is a **test-only** helper today. Raw-string, Go multiline-comment, Unicode and CRLF examples compare exact source styling to a fresh analyzer, including cases where syntax styling propagates beyond the removed line. A subsequent closing-delimiter edit is rejected by the fast-path classifier, takes the canonical fallback, and still matches fresh source analysis. The initial code-fence row builder was also shown to produce exactly the same styled cells and source atoms from the source highlighter's cached injection output; a warm 15-line highlight costs about 11–13 ms. The current separate `highlight_snippet` path still reparses the complete code block and must be avoided on an ordinary edit's viewport frame.

These component times suggest a low-tens-of-milliseconds route even after pane framing, but **must not be summed as an end-to-end measurement**: the prototypes are not yet integrated through `EditorPane`, and p99 over at least 100 edit/undo cycles remains an acceptance condition for task 018/019. Nothing expensive is intentionally deferred to the next frame: the bounded source edit updates the code tree synchronously, and source lines queried immediately afterward match fresh analysis. Full resize/reload/delimiter changes may still take a measured wide path.

## Production architecture recommended

1. Normalize `d`/`c` geometry, but **not `y`/copy geometry**, when all source-backed display text on a physical source line is selected. A 15-line function selection should become one contiguous `TextEdit` including its newlines. A partial wrapped source line remains characterwise. Keep the user-visible four modes and all register/yank semantics behind the same core session. Use the existing `hjkl_buffer::Edit::Replace` / `Editor::mutate_edit` with one undo group rather than a full `replace_all`; this stays entirely inside `vim.rs`.
2. Add a conservatively proven interior-fence transaction to `LiveDocument`: authoritative Vim rope edit first; then `Highlighter` edits its retained code-injection tree and line-start index; `RetainedBlockModel` updates the fence's content/end spans, definition offsets and later block spans; `RetainedRows` splices only affected code rows and adjusts row/source prefixes. Publish a `MutationOutcome` only after those synchronous derived updates are coherent. The same `EditorSession` path serves standalone and embedded `EditorPane` hosts. If preconditions fail, use the full existing parser/builder path in the **same transaction**.
3. Keep one row store per Markdown block. Extend the fence row chunk with local splice boundaries and source-offset segments rather than adding an independent rendered document. Segment lookup at row read rebases provenance lazily; neighboring segments can coalesce. The test that initially shifted every subsequent rendered row failed on the link appendix: its rows can appear later but point to source **before** the edit. Source offsets must be applied by source ownership, not by rendered row order. Preserve the existing footer/link-index builder's source-aware behavior.
4. Project a short Select directly from indexed rows and already-known source-backed endpoints. Construct visible intervals and operation ranges from the affected row span, not all ~46,000 rows/atoms. Preserve the public full-layout and full-selection APIs; their implementation may assemble a complete result on explicit request, while pane drawing and key handling use the same indexed core projection. Do not cache a second mutable selection model in App. Avoid asking for the same full projection twice per frame.
5. Treat syntax propagation and global Markdown relationships explicitly. A raw string/comment edit can change styles beyond the text splice; use the injection tree's changed ranges (or a conservative wider range) to rebuild the affected code rows synchronously. Fence delimiter, uncertain nesting, front matter, footnote/reference-definition and other global changes fall back to the complete path. The internal Markdown tree may stay positionally edited only when the fence body is provably opaque; a later structural edit must reconcile it and all output must compare to a fresh parse.

## Cost and risk

The change adds narrowly scoped source and row invalidation rules plus a per-fence offset index. It does **not** require a new dependency or change the public crate facades. The difficult correctness boundaries are Markdown fence recognition, tree-sitter changed-range propagation, CRLF/UTF-8 offsets, source-less decorations, links/footnotes outside document order, and repeated edit/undo. The test-only prototype proves the chosen ordinary Rust/Go operations and representative edge cases, but it does not prove that every arbitrary edit is local. The implementation must retain the full builder as a differential oracle, use conservative fallback, and add property/seeded sequences for all four modes, selection shapes and widths.

The candidate's task-013 peak RSS ranges from approximately 205–230 MiB after an edit, versus approximately 200–223 MiB on main; flat sessions are approximately 160 MiB in both. A direct capacity sum of the existing 45,974-row `RetainedRows` store is 60,071,231 bytes (row vector storage, text, spans, atoms, line numbers, jump targets, links, fence regions and prefix), and constructing a second such store in the diagnostic increased that process's RSS by 66,801,664 bytes. This is a capacity estimate and an RSS delta, not a complete heap profile; the copied full layout and allocator state were already present. The proposed fast path retains the **existing** single injection-tree cache, block model and row store and adds small offset-segment metadata rather than another complete 1 MiB text or layout. The prototype reads 16 Select rows or 41 viewport rows; the full note has ~45,974 rows before the edit and ~45,959 after. Production repeated-run RSS is part of final acceptance, and a material increase from new offset metadata would require review. Do not trade a large memory increase for latency without explicit review.

The task-013 PTY trace could not reproduce the user's kitty visual hitch, despite matching main's serial output-byte counts and recording no active flush pause. Physical kitty presentation is unmeasured; task 016 still owns that investigation and must not infer a fix from this GO decision. If integration of the bounded path requires stale editable rows, a parallel renderer/text owner, or cannot meet the exact differential/p99 gates, return to `PLAN_CHANGE_REQUIRED` for a source-centric viewport or partial-rollback decision instead of weakening acceptance.
