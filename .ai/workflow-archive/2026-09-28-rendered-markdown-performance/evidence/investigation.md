## Verified source paths

1. `rendered/mod.rs::render_code_fence` calls `syntax::highlight_snippet` for each fence. `syntax/mod.rs::highlight_snippet` invokes `Query::new` each call. The same `Highlighter` already has `query_cache` keyed by `LangDef` canonical name for source injections. The study measured 18.7 ms for a Rust query and 86–88% of code-heavy first-frame time in query compilation.
2. `session.rs::render_layout` rebuilds a full `BlockModel` and `RenderedLayout` when its cache is invalidated or width changes, then calls `nav::enter_rendered`. In `nav.rs::enter_rendered_at_offset`, an unmapped source cursor reaches the `nearest_after` fallback. The `enter_rendered` callback counts newlines in the source prefix for each candidate row. Thus the cost can approach rendered rows times source bytes. The study's blank-first-line control changed a 1 MiB first frame from about 200 ms to 2.6–3.2 s; it is cursor-position dependent rather than universal.
3. Both `save_if_version` and the regular save path invalidate the rendered layout after a successful save even though no text changes. Edits, width changes, and reloads also invalidate; theme, search, tab switch and height-only resize do not. The public `EditorPane::render`/`App::render_owned` path is synchronous on its calling thread, so a long rebuild stalls either host.
4. `highlight_snippet` filters all capture spans for every code line, causing superlinear work for one huge highlighted fence. Source `Highlighter::collect_spans_in_range` reparses every overlapping injection for every visible frame. These are independent of the two headline fixes and matter for large-fence editing.
5. The current 1 MiB release fixture in `perf/fixtures.rs` is repeated prose with no fenced blocks or tables. Its passing 350 ms contract does not exercise the content classes in the report. The study observed 1 MiB table retained-layout heap of 135 MB and process peak RSS of 287 MB, above the published 64 MiB / 192 MiB limits. These are separate capacity risks.

## Quantitative judgement

The report is accurate for the tested version, machine, fixtures and public-pane call path. The five-run study places first 350 ms failures at 16 KiB many small fences, 128 KiB one Rust fence, 144 KiB mixed, 256 KiB lists, and 448 KiB tables; plain prose stayed below the limit through 1 MiB. Its five largest vault notes were 177–327 ms except a 162,249-byte code-heavy note at 454 ms. The temporary two-fix experiment brought those five to 120–155 ms, but left the 1 MiB mixed fixture at 459 ms and a 512 KiB single Rust fence at 1,816 ms. Therefore fixing only query compilation and cursor lookup would not establish a universal 350 ms guarantee or remove every long synchronous pause.

The study's exact worst-of-five thresholds depend on host load, fixture content, cursor location and pane width. Its huge code fixture contains error-heavy synthetic Rust, which may overstate parser recovery cost for valid Rust; query compilation is independent of code validity. No product code was changed during this investigation.
